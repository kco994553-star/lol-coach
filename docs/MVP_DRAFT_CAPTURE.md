# Manual draft capture(수동 픽창 기록)

2026-10-05. 기존 Frozen(동결) TEAM_DRAFT / REC-REQ-013의 입력 수집만
구현한다. 개인 서버에서 직접 본 픽·밴·불확실한 역할을 저장하는 경로다.
자동 감지·Riot API·League Client(게임 클라이언트) 연동·게임플랜·실시간
코칭은 이 기록의 capability(지원 능력)가 아니다. 실제 코칭 N=0,
accuracy(정확도)=null을 유지한다.

## 사용 경로

기존 개인 루프백 서버와 접속키로 접속한 뒤 ‘수동 픽창 기록’을 연다.
새 기록에 제목, 작성자, 직접 확인한 정보와 불확실성을 입력하고 명시적으로
저장한다. phase(진행 단계), patch(패치), 관찰 시각을 모르면 빈칸으로
남긴다. 선택한 champion(챔피언)과 role(역할)은 직접 입력한 선언이다.
빈 목록은 ‘아직 입력하지 않음’이며, 픽·밴이 없음을 확인한 결과가 아니다.
UNKNOWN(알 수 없음)을 자동으로 확정값이나 confidence(신뢰도)로 바꾸지 않는다.

PLAYER(플레이어) perspective(시점)를 선택해도 원본이 검증되는 것은 아니다.
모든 기록은 UNVERIFIED(미검증), gameplan(게임플랜) NOT_GENERATED(미생성),
coaching_enabled(코칭 활성화)=false다. 당시 관찰 시각과 서버 저장 시각은
서로 다른 필드다. 모르는 게임 시계·패치·의도·판단을 생성하지 않는다.

저장 목록에서 기록을 열고 편집하면 다음 저장은 새 immutable snapshot(불변
저장본)을 만든다. 현재 저장 기준이 다른 탭에서 바뀌면 REVISION_CONFLICT
(버전 충돌)를 표시하고 초안을 유지한다. 저장 요청 중 추가로 편집한 내용은
서버 응답이 도착해도 초안으로 남는다. 저장하지 않은 변경을 버리는 이동은
native confirmation(실제 브라우저 확인창)을 사용한다.

POST/PUT save(저장)는 1개의 유효한 Idempotency-Key(멱등성 키)를 요구한다.
서버에 저장됐지만 응답을 받지 못한 경우 화면은 최초 요청의 키·본문·저장 기준을
그대로 유지한다. 사용자가 다시 저장하면 동일 요청은 최초 저장본을 반환하며 새
기록이나 버전을 만들지 않는다. 같은 키로 다른 본문을 보내면
IDEMPOTENCY_CONFLICT(멱등성 충돌), 새 키로 오래된 저장 기준을 보내면 기존처럼
REVISION_CONFLICT(버전 충돌)다. 성공 응답을 확인한 뒤에만 다음 편집 저장용 키를
새로 만든다. 이 동작은 구조 2의 기존 불변 저장본을 receipt(처리 증표)로 사용하며
DB schema(구조), 검증 상태, 분석·코칭 활성화 계약을 바꾸지 않는다.

이력 미리보기는 read-only(읽기 전용)다. 과거 이력을 조회해도 현재 편집 내용과
다음 저장 기준은 바뀌지 않는다. JSON download(다운로드)는 실제 저장본을
내보내며 미저장 초안을 저장했다고 표현하지 않는다. 명시적인 null(알 수 없음)
행, 기존 배열 순서와 미편집 원본 문자열을 수정 없는 저장에서 보존한다.
기존 행의 값을 비우면 그 행은 null로 남으며, 다른 역할을 자동 생성하지 않는다.

삭제는 현재 기록과 모든 버전을 제거한다. 삭제 중 내려받기와 이력 내보내기는
차단하며, 늦게 도착한 이전 조회가 삭제된 기록을 다시 표시할 수 없다.
서버의 현재 DB에서 제거하는 동작이다. 이미 만든 개인 backup archive(백업
파일)와 pre-migration recovery copy(변경 전 복구 파일)는 따로 보관된다.
과거 백업 안의 자료까지 삭제했다고 주장하지 않는다.

## 저장·통합 경계

Main SQLite(주 데이터베이스) schema(구조) 2의 독립 draft_captures /
draft_snapshots 테이블을 사용한다. 기존 Store(저장소)와 TEST(시험용) session
(세션)·case(사례)·job(작업) 테이블 및 엔진은 그대로다. 수동 기록 ID는 기존
분석 세션 ID가 아니며, 기존 사례·분석 API(호출 경로)에 넣을 수 없다.
Research(자료) / Knowledge(지식 후보) DB는 기존 구조 2를 유지한다.

기존 Main 구조 1을 여는 경우 정확한 구조와 내용부터 검사하고, private(비공개)
0600 권한의 실제 복구 복사본을 비덮어쓰기 방식으로 만든 뒤 구조 2를 적용한다.
복사 실패는 원래 구조를 유지하며, 변경 실패는 실제 복구본을 남긴다. 새 빈
설치가 과거 자료의 백업을 만들었다고 표현하지 않는다.

기존 ZIP backup format(백업 형식) 1과 정확히 두 DB 파일을 유지한다.
실제 Main 구조 1/2와 Research 구조 1/2만 정확한 DDL(테이블 정의), 외래키,
기록 내용, 해시, manifest(파일 목록) 버전 일치 검사 후 복구할 수 있다.
백업 검사는 앱 생성자·분석 엔진·작업 복구·구조 변경을 실행하지 않는다.
원래 TEST 내용 검사 함수와 Frozen/옛 검사·예상값·근거는 변경하지 않는다.

## 검증 근거와 제한

| 검증 | 범위 |
| --- | --- |
| Storage(저장) | 새 31개 + 기존 Store 11개 통과. 큰 손상 버전 번호의 메모리 반례와 최초 실패 보존 |
| HTTP(실제 호출) | 토큰·Host·Origin·모드 분리·불변 이력·CAS(버전 비교 저장)·삭제·한도 및 재시작 후 동일 POST/PUT replay(재실행) 17개 통과 |
| Backup(백업) | 새 19개 + 기존 23개 + Knowledge 19개 통과. 초기 실패와 검사 자료 수정 이력 보존 |
| Synthetic UI(합성 화면 검사) | 기존 7개 통과 후, 독립 검토가 명시적 UNKNOWN 행 손실을 발견. 배열 0/4→4/4, 원본 문자열 1/4→4/4 수리 검증과 기존 7/7 유지. 응답 유실 재시도 0/1→1/1 |
| Browser(브라우저) | 실제 개발 서버·HTTP·SQLite·native(실제) 저장·내보내기·취소·충돌·390px·저장 후 응답 유실 경로는 실제 Actions(원격 검사) 완료로만 확인. 로컬 첫 실행 파일 부재 실패는 보존하며 PASS로 계산하지 않음 |
| Real match(실제 경기) | Player reference(독립 플레이어 기준)·State(상태)·Decision(판단)·Coach(코칭) N=0, accuracy=null |

실제 경기 Evidence(근거)는 이 기능의 시안·자동 검사 자료와 별도다.
현재 player reference(플레이어 기준) 및 행동 전 문맥 의존성만
PARKED_EXTERNAL(외부 입력 대기)이다. 이 입력 저장 기능의 성공을 실제
gameplan(게임플랜)이나 코칭 정확도 검증으로 계산하지 않는다.
최신 현재 실행·실제 CI 링크와 최종 해시는 CURRENT_HANDOFF와 새 근거를 따른다.
