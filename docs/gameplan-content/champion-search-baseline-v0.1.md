# 2. 게임플랜 — 챔피언 검색·기본 방향성 확장 설계 v0.1

기준일: 2026-10-25 KST
문서 ID: GP-CHAMPION-SEARCH-BASELINE
상태: DESIGN_BASELINE(설계 기준안). 사용자 승인 범위의 구체화이며 신규 제품 코드 구현·테스트·배포 완료가 아니다.
코드 확인 기준: `944c0ef64e59e94b19d3ebe5694efefae41cc8cc`.
적용 관계: 기존 게임플랜 v1.3 출력 기준과 `backend-design-v1.md`, `tag-criteria-v1.md`의 보완 문서. 기존 문서 버전·2.1~2.7의 의미를 바꾸지 않는다.

## 1. 목적과 범위

사용자가 승인한 방향은 게임플랜 안에 챔피언 검색을 넣고, 10픽을 입력하지 않아도 선택한 챔피언의 기본 방향성·라인전 또는 초반 정글·운영·한타를 보여주는 것이다. 이후 선택한 챔피언과 포지션을 조합 분석으로 연결한다.

단순 스킬 소개가 아니라 플레이 목적, 실행 방법, 성립 조건, 실패 비용과 대안을 읽을 수 있는 기본 게임플랜을 제공한다. 조합을 모르는 상태를 유리·불리·경합으로 바꾸지 않는다.

이번 문서는 검색 동작, 화면 흐름, 자료 계약, 기존 코드 연결 경계, 실패 처리와 인수 기준까지 다룬다. 전 챔피언 전술 작성, 부분 조합 분석 엔진, 실시간 코칭, 픽·밴 추천, 룬·아이템 추천, 새 서버 도입은 이번 확장 범위가 아니다.

사용자 승인 사항과 설계 선택을 구분한다. 한 화면의 두 보기, 검색 정렬, 상태 이름, 아래 세부 요구 ID는 이번 설계안의 선택이며 사용자가 직접 승인한 세부사항으로 기록하지 않는다. 전술 후보·전술 승인 이력도 변경하지 않는다.

## 3. 선택한 접근

| 접근 | 장점 | 문제/판정 |
|---|---|---|
| 별도 챔피언 소개 페이지 | 빠른 정보 제공 | 실제 게임플랜과 중복되고 조합별 변경 연결이 약함. 채택하지 않음 |
| 검색할 때마다 AI 자유 생성 | 다양한 문장 생성 | 재현성·비용·근거·품질 관리에 불리함. 기본 경로로 채택하지 않음 |

검색과 기본 보기에는 별도 AI 호출·Riot 계정 조회·LCU 연결을 요구하지 않는다. 배포된 챔피언 목록과 버전이 있는 작성 자료를 사용한다. AI를 자료 작성 보조에 쓰더라도 검토와 게시 과정을 거쳐야 하며 조회할 때 임의 내용을 만들지 않는다.

## 5. 사용자 흐름과 화면

게임플랜 안에 `챔피언 기본`과 `조합 맞춤` 두 보기를 둔다. 새 방문의 기본 진입은 챔피언 기본으로 제안하되, 기존 조합 분석 링크·저장된 분석 진입은 기존 보기로 이어진다. 별도 최상위 메뉴를 만들지 않는다.

기본 흐름:
`챔피언 검색 → 챔피언 선택 → 포지션 확인 → 기본 방향 → 라인전/초반 정글·운영·한타 → 이 챔피언으로 조합 분석`.

### 검색 동작

- 공식 한국어·영어 이름, 등록된 별칭으로 검색한다. 별칭은 챔피언 ID에 연결하며 임의로 추측하지 않는다.
- 공백·대소문자·등록된 문장부호 차이를 정규화한다. 정확히 일치 → 앞부분 일치 → 부분 일치 순이며 동순위는 정해진 이름/ID 순으로 안정 정렬한다. 승률·강함 순위가 아니다.
- 검색 결과는 이름·선택 가능한 포지션·기본 설명 지원 상태를 보여준다. 챔피언 목록 등록과 전술 콘텐츠 지원은 별도다.
- 한 포지션의 자료만 있으면 그 포지션을 눈에 보이게 미리 선택할 수 있으나 사용자 변경을 허용한다. 여러 포지션이면 선택 전 역할별 전략을 확정하지 않는다.
- 공식 역할군 태그를 TOP/JUNGLE/MID/BOTTOM/SUPPORT의 실제 포지션으로 자동 변환하지 않는다. 지원 포지션은 별도 자료에 명시한다.
- 미지원 포지션도 선택할 수 있고 자료 부족을 알린다. 다른 포지션의 설명으로 대체하지 않는다.
- 검색어 입력만으로 확정 선택하지 않는다. 검색 오류와 자료 부족, 검색 결과 없음은 서로 다른 상태다.

### 기본 노출

상단: 선택한 챔피언·포지션 / `기본 방향` 표시 / 핵심 방향 한두 문장 / 자료 패치·검토 상태.

각 단계: `짧은 태그 → 한줄평 → 역할이 정해진 5개 행동 → 독립적으로 읽히는 코칭 본문 → 선택적 상세`.

본문을 다시 숨기거나 5개 행동의 이유를 기계적으로 나열하는 설명으로 대체하지 않는다. 사용자가 어떻게 라인전·운영·한타를 풀어갈지 자연스럽게 서술한다. 태그는 기본 2개를 목표로 최대 3개이며 근거가 부족하면 줄인다. 행동과 별도의 전술 판단을 태그에서 생성하지 않는다.

기본 보기의 전체 조합 영역은 `조합 미입력 — 팀 방향은 아직 판단하지 않음`으로 표시한다. 팀 비교표의 구조와 의미를 재사용하되 수치·우열·상대 강약을 채우지 않는다. 10픽을 입력하면 기존 비교표·사용자 역할 코멘트를 정상 출력한다.

### 조합 분석으로 이동

버튼을 눌렀을 때만 선택한 챔피언·포지션을 사용자 픽으로 전달한다. 나머지 9픽은 미입력으로 남긴다. 더미 챔피언으로 10픽 입력 검증을 우회하지 않는다.

기존 작성 중인 조합이 있다면 그대로 보존한다. 같은 슬롯의 다른 픽을 바꾸거나 중복 챔피언·사용자 포지션 충돌이 생기는 경우, 변경 전 내용을 보여주고 사용자가 명시적으로 교체해야 한다. 단순 보기 전환은 입력을 수정하지 않는다.

조합을 일부만 입력한 상태는 `입력 중`이다. 새 부분 조합 엔진을 만든 것으로 취급하지 않는다. 전체 조합 분석은 기존 필수 입력 계약을 충족한 뒤 실행한다. 기본 보기로 돌아와도 작성 중인 조합을 잃지 않는다.

## 6. 내용의 구분과 비교 원칙

`기본 방향`은 챔피언이 목표로 삼는 이득과 조건부 수단이다. `이번 판 계획`은 제공된 조합과 명시된 가정에 따라 실제로 채택한 설명이다. 둘은 같은 프로필 버전을 참조한다.

기본 문장을 조합 결과 위에 무조건 덧붙이지 않는다. 최종 실행과 기본 원칙이 충돌하면 이번 판 행동을 앞세우고 기본 원칙의 적용 조건이 왜 달라졌는지 설명한다. 이전 행동 태그도 제거한다.

유지/강화/부분 수정/전환은 명시된 비교 규칙과 주장 ID가 있을 때만 출력한다. 현재 `change.kind=LIMITED`를 화면에서 임의 분류하지 않는다. 분류할 수 없으면 `변경 분류 제한`이라고 표시하고 확인된 차이만 설명한다.

아군·상대·레벨·체력·쿨다운·웨이브·위치가 없으면 미확인이다. 조건부 문장을 현재 관측으로 표시하지 않는다. `교전이 필요함`과 `지금 교전할 수 있음`을 구분한다. 기다리면 손실이 커지더라도 실행 조건을 이미 잃었다면 무리한 진입 대신 웨이브 정리·귀환·지원 요청 등 검토 가능한 복구 방향을 설명한다.

공식 기술 설명은 작동 기전의 근거다. 상성 우세·전술 최적성·실경기 효과의 검증으로 승격하지 않는다.

## 7. 데이터와 연결 계약

구현 시 기존 자료를 읽는 Adapter(변환 계층)를 우선하고 전술 원문을 별도 저장소에 복제하지 않는다. 아래는 설계 필드이며 현재 코드에 모두 구현된 필드라고 주장하지 않는다.

| 자료 | 필수 정보 |
|---|---|
| 검색 목록 | 게임/모드, 자료 버전, 정규 챔피언 ID, 한국어·영어 이름, 별칭, 지원 포지션, 초상화 참조 |
| 기본 프로필 | ID·버전, 챔피언 ID·포지션, 적용 패치/검토 범위, 출처·해시, 전술 검토 상태 |
| 단계 자료 | 목적, 실행 방법, 성립/중단 조건, 실패 비용, 대안, 한줄평, 기존 역할 슬롯에 맞는 5개 행동, 코칭 본문, 주장/근거 ID |
| 기본 결과 | `view_mode=BASELINE`, 선택 정보, 자료 버전 묶음, 단계별 지원 상태, 단계별 delivery, `composition=null` |
| 조합 결과 | 기존 계약 보존, 참조한 기본 프로필 버전, 조합/가정 스냅샷, 최종 delivery, 제한된 변화 비교 |
| 추적 정보 | 입력·정규화 버전, 자료/프로필/규칙/표현 버전, 적용/제외/보류 이유, 출력 위치 |

기본 보기에는 독립 입력 스키마를 둔다. 10픽 조합 스키마를 느슨하게 만들어 기존 분석의 검증을 약화하지 않는다. 표시 단계는 이미 계산된 delivery만 읽고 전술을 재판정하지 않는다.

초기 구현은 기존 정적 웹/JavaScript 경로를 유지한다. 검색 목록과 기본 프로필은 같은 배포 묶음에서 읽되 패치 적합성과 지원 범위는 각각 검사한다. 검색할 때마다 새로운 서버·DB·모델 호출을 도입하지 않는다.

동일한 정규 입력과 게임/모드·자료·프로필·규칙·표현 버전 묶음은 같은 의미의 결과를 만든다. 생성 시각 같은 진단 메타데이터는 이 비교에서 제외한다. 캐시 키에도 이 범위를 반영하여 다른 포지션·패치·자료 버전을 섞지 않는다.

Riot Data Dragon의 자료 버전은 지역 클라이언트 버전과 항상 같지 않다. 최신 자료 URL을 읽었다는 이유로 기존 전술 프로필을 최신 패치 검토 완료로 바꾸지 않는다. 공식 역할군·스킬 데이터와 작성 전술의 상태도 분리한다.

## 8. 실패·자료 부족 상태

| 상태 | 사용자 표시와 동작 |
|---|---|
| 초기/검색 중 | 검색 안내, 실제 로딩 상태, 키보드 접근 유지 |
| 검색 결과 없음 | 일치하는 챔피언 없음. 기존 선택·조합은 삭제하지 않음 |
| 목록 로드 실패 | 검색 자료를 불러오지 못함, 재시도 제공. 기존 조합 경로를 불필요하게 막지 않음 |
| 포지션 미선택/충돌 | 포지션 확인 필요. 임의 역할로 전략을 출력하지 않음 |
| 기본 프로필 없음 | 챔피언은 찾았지만 이 포지션의 기본 방향 자료가 부족함 |
| 특정 단계만 부족 | 해당 단계만 자료 부족. 다른 단계의 유효한 내용을 지우지 않음 |
| 패치 부적합/기전 근거 누락 | `SOURCE_REVIEW_REQUIRED`. 현재 적용 가능한 계획처럼 제공하지 않음 |
| 기본만 지원 | `BASELINE_ONLY`. 특정 상대·조합 분석 완료를 암시하지 않음 |
| 공통 원칙만 존재 | `GENERAL_ONLY`. 챔피언 이름만 붙여 고유 코칭처럼 표시하지 않음 |
| 5개 행동 계약 불완전 | 계약 오류·검토 필요. 문장을 자동 생성하거나 잘라서 개수를 맞추지 않음 |

기존 프로필에 문단만 있다면 그 문단은 작성 자료로 재사용할 수 있으나, 그것만으로 새 5개 행동 계약을 충족했다고 표시하지 않는다. 현재 패치 확인이 안 된 자료를 읽기용으로 남기는 경우 원래 패치와 재검토 필요 표시를 유지하고 현재 행동 지시·태그와 분리한다.

## 9. 화면 문구 예시 — 작성 초안

아래는 기존 케이틀린 기본 프로필을 바탕으로 정리한 표현 예시이며 최신 패치 전술 검증 결과가 아니다. 실제 UI·배포·지원 완료를 뜻하지 않는다.

```text
2. 게임플랜
[챔피언 기본]  [조합 맞춤]

챔피언 검색: 케이틀린
케이틀린 · 바텀
기본 방향 / 조합 미입력 / 작성 전술 · 효과 미검증

상대가 막타를 먹으러 나오는 순간의 압박을 이득으로 잇는다.
반격을 감당할 수 없다면 밀어붙이는 것부터 고집하지 않는다.

라인전: 막타 접근 견제 · 반격 확인
운영: 포탑 압박 검토 · 측면 경계
한타: 공격 거리 유지 · 퇴로 확보

[라인전] [운영] [한타]
각 영역: 한줄평 → 5개 행동 → 코칭 본문 → 상세

[이 챔피언으로 조합 분석]
```

라인전 코칭 본문 예시:
케이틀린으로는 상대가 막타를 먹으러 나오는 순간에 공격하고, 그 압박을 웨이브와 포탑에 연결하는 방향을 먼저 본다. 다만 내가 한 대 때리는 동안 상대 두 명에게 같이 맞는 자리라면 사거리가 길다는 이유만으로 앞으로 나가지 않는다. 아군 서포터가 같은 상대를 건드릴 수 있는 거리인지 확인하고, 상대의 반격을 감당할 수 있는 자리에서 압박을 이어간다. 압박할 여건이 없으면 체력을 소모하며 밀어붙이기보다 막타 접근과 다음 공격 위치부터 남긴다.

이 예시는 전체 프로필 납품본이 아니다. 5개 행동·각 단계 본문·근거 연결을 완성하기 전에는 공개 지원 범위를 확대하지 않는다. 태그도 실제 최종 행동과 연결된 것만 출시한다.

## 11. 구현 순서와 완료 경계

첫째, 기존 프로필의 지원 상태를 검사하고 단독 기본 입력/결과 계약 및 검색 정규화를 테스트한다. 둘째, 검색→기본 방향→조합 이동의 한 사용자 흐름을 연결하고 기존 화면의 회귀를 확인한다. 셋째, 기존 4명 재사용 후보를 단계별 인수 기준으로 보강한다. 카이사 등 추가 챔피언은 프로필과 검증 사례가 준비된 범위만 확장한다.

제품 코드 변경 상태: NOT_STARTED(이번 신규 확장). 기존 기능의 구현 이력을 0으로 되돌리지 않으며, 기존 자산이 있다는 이유로 새 흐름을 구현 완료로 집계하지도 않는다.

설계 이후 남은 일: 단계별 5개 행동·코칭 원문 보강, 구체적 변환 함수/테스트 경로 결정, 구현, 브라우저 검사, 배포, 실사용 검토. 전술 효과는 별도 실경기 증거가 필요하다.

## 12. 문서 최신화 기준

이번에 GitHub·Notion에 기록할 최소 기준은 범위·기능 대응·화면 흐름·입출력·실패 상태·인수 기준을 모두 문서화한 상태다. 이는 설계 완료의 관리 기준이지 제품 출시 기준이 아니다.

GitHub의 이 문서를 상세 설계 원본으로 두고 Notion은 같은 문서 ID·버전·코드 확인 기준과 원문 링크를 기록한다. Notion 관리자에는 확장 범위와 상태를, 상세에는 설계를, 그래프에는 새 진입 경로를 표시한다. 기존 2.1~2.7과 1/3 영역은 재번호화하지 않는다.

문서 PR을 열었다면 병합 전 상태를 명시한다. Notion 갱신을 GitHub main 반영이나 앱 배포로 표현하지 않는다. 문서 작성만으로 기존 전체/프론트엔드 진행률을 올리지 않는다. 이번 갱신은 수동 실행이며 자동 동기화·예약을 설정하지 않는다.
