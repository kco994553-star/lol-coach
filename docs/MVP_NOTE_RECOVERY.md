# 저장 노트 이력을 편집 초안으로 복구

2026-10-05. 기존 저장 노트 이력의 명시적 복구 경로다. API(서버 인터페이스)와
schema(저장 형식)를 바꾸거나 과거 노트 행을 덮어쓰지 않는다.

1. 자료·복기 노트에서 현재 노트를 열고 저장 버전 목록과 과거 버전을 조회한다.
2. **조회한 내용을 편집 초안으로 복사**를 누른다. 수정 중인 초안이 있으면 실제
   확인 창에서 교체 여부를 결정한다. 취소하면 현재 초안이 그대로 남는다.
3. 조회한 known(알고 있던 정보)·intention(의도)·alternative(대안)·outcome(결과)의
   네 문자열을 편집기로 복사한다. HTML textarea(다중행 입력창)의 기존 동작으로
   CRLF/CR(줄 끝 문자)은 LF(줄바꿈)로 정규화된다. 원본 이력·다운로드·출처 해시는
   원래 바이트 그대로 보존된다. 이 단계에는 저장 요청이 없다.
4. 수정 후 기존 **노트 저장** 버튼으로 저장한다. CAS(동시 변경 확인)는 현재
   불러온 최신 노트 버전을 사용하며 과거 조회 버전을 저장 기준으로 사용하지 않는다.
   다른 창에서 먼저 저장했다면 실제 충돌을 표시하고 복구 초안을 유지한다.

자료·구간·조회 버전·화면 이동, 로그아웃, 삭제 또는 저장 중에는 유효하지 않은
조회 내용으로 복구하지 않는다. 복구의 새 저장은 기존 버전 다음에 추가되며, 과거
노트와 Knowledge(지식) 후보의 고정 출처·해시는 바뀌지 않는다. 복구가 노트 내용의
정답성이나 실제 Player(플레이어) 관찰을 검증하는 것은 아니다. 사후 outcome(결과)은
의사결정 입력으로 승격하지 않는다. 실제 Coaching(코칭) N0 / accuracy(정확도) null.

검증은 고정 Node VM(모의 화면) 사례와 실제 Chrome(브라우저)·HTTP(통신)·SQLite
(저장소) 사례를 구분한다. 정확한 다국어 문자열, 취소, 자동 쓰기 없음, 최신 버전
저장/실제 충돌/과거 고정 출처 보존, 오래된 조회 응답과 390px 흐름을 검사한다.
첫 실패와 수리 및 실제 실행은 additive(이력 보존 추가) 증거로 남긴다.

첫 실제 Actions(자동 검증)37270809307에서는 서버 회귀와189개 입력 해시가
일치했고 브라우저84개 중 삭제 후 상태 비교가 실패했다. 삭제 직후 저장 내용을
비운 다음 목록을 갱신하고 완료 알림을 바꾸는 정상 경로를 너무 일찍 비교한
검사 문제였다. 독립 Node VM(모의 화면) 재현에서 바뀐 키는 notice(알림) 하나였다.
완료 알림까지 기다린 다음 늦은 실제 조회 응답을 풀도록 검사 시점만 수정했다.
