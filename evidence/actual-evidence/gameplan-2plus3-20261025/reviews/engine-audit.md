## Minimal extension contract proposal (implementation choice, not adoption)

Introduce input-v5 as exact v4 keys plus required `situation`. Keep v1–v4 strict field sets and historical meanings unchanged. `situation` is versioned `lol-coach-situation-v1`; every known datum carries `{status,value,source,observed_at}`. Status is observed/assumed/unknown/stale. Unknown has null value/source/time. Assumed is an explicit user choice, source USER_ASSUMPTION, no observation timestamp. Observed/stale retain nonempty source and valid observation time; stale remains serializable and inspectable but cannot supply a current value. No transport TTL reused as gameplay freshness; no arbitrary global seconds. Freshness policy remains per-data and source based; do not claim the first schema verifies whether an external observation is fresh. No live inputs become observed automatically.

Minimal fields: ally/enemy jungle location class; wave direction/size/manipulability; own health/mana or a clearly scoped resource constraint; support/follow-up; combat context; actual contribution and coarse arrival order; threat reach; allied carry risk and feasible enemy carry disruption. Unknown is permitted independently for every field. A small implementation may use scoped categorical values without numeric ETA/probability; do not imply health/mana/skill knowledge from a single broad label. Threat candidates can retain existing champion/skill evidence and indicate reach/participation uncertainty; do not rank alphabetic names as threats.

Proposed ownership:

- `web_r4/loading-situation.js`: pure strict validator, status/provenance normalization, explicit legacy-assumption adapter and effective-values/constraint projection. It is not a new independent tactic engine.
- `web_r4/loading-engine.js`: accept v5 and preserve normalized situation in report input; share existing output/report path. Preserve v1–v4 validation exactly. Require module in Node/HTML dependency order.
- `web_r4/loading-planboard.js`: consume situation once for action feasibility, goal conflict and combat objective. Reuse existing trivalent helpers, candidate scope and evidence. Final phase decision owns goal, selected action, reason, prohibitions, switch/abort and uncertainties; delivery and tags derive from that node. Keep baseline direction explicitly separate. A tank objective can be PROTECT_ALLY or DISRUPT_ENEMY_CARRY with WAIT/REPOSITION fallback, never class-only unconditional dive. ADC objective connects surviving to attack space/time; no automatic fight refusal.
- `web_r4/loading-presentation.js`, `loading.js`, `loading-coach-view.js`: versioned serialization/restore, display uncertainty/explicit assumption in the same screen, complete reset and reanalysis, explicit top team/user responsibilities and broader fight heading. UI does not select tactics or rank threats.
- Add a GP23 situation/output contract, input/decision regressions and paired production evidence. Existing `gameplan-delivery-v1` either gains backward-compatible optional nodes without changing required fields, or introduce a separate GP23 payload alongside it; do not relabel the existing report/version without a migration decision. If v5 fields travel in links, update presentation allowlist and route validation deliberately.

Required bounded verification before completion: v1–v4 exact regression; serialize/reload/reset all statuses; observed with no source/time rejected; stale cannot grant current AWAY/safe; unknown both jungles never invents location; nearby jungle+incoming large wave; away jungle+low resources; flow incompatible with trim/freeze; no allied follow-up; tank distract-vs-cover switch; nominal advantage with unavailable ally; unknown skills/terrain; action/headline/tag coherence; exactly five actions, max two tags; unsupported champions retain bounded fallback. Browser validates input→decision→view→change→reset and narrow widths. These checks establish implementation consistency only, not coaching accuracy or real-game efficacy.
